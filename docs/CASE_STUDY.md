# Case study: Victor — a voice-driven AI race engineer for Assetto Corsa on Linux

## The problem

[CrewChief](https://gitlab.com/mr_belowski/CrewChief) and [Crew Chief V4](https://thecrewchief.org/)
are the reference implementations in this space: they read Assetto Corsa's
shared memory (`acpmf_physics` / `graphics` / `static` / `crewchief`) and
provide spotter calls, fuel/tyre alerts, and lap summaries with synthesized
speech. Both are Windows projects.

On Linux, running AC itself via Steam + Proton already works well, but
CrewChief depends on Windows Speech Recognition (SAPI) for voice input — a
component that doesn't exist outside Windows, and running the app inside the
same Wine/Proton prefix as the game doesn't fix that, because Windows speech
recognition needs system services Wine doesn't provide. In practice,
CrewChief's voice interaction isn't viable on Linux without extra hardware
or workarounds.

The other limitation, independent of the operating system, is that
CrewChief's voice is a pre-recorded announcer with fill-in-the-blank
phrases: fixed sentences from a closed grammar, not a response generated in
context. Free-form questions ("how are the tyres doing?" vs. "give me the
tyre status") don't work the same way unless they match the exact grammar.

Victor fills that specific gap: speech recognition and synthesis that run
natively on Linux (no SAPI anywhere in the pipeline), Spanish responses
generated by an LLM instead of templates, and the same data source CrewChief
uses (AC's real shared memory), so the spotter, alerts, and strategy
calculations have the same data fidelity. It doesn't replace CrewChief's
research on spotter zones, alert thresholds, or pit strategy — it reuses
that and builds the voice layer on top, on a stack that actually runs on
Linux.

## Architecture decisions and their trade-offs

### Why the SHM reader is written in C, running under the same Proton as the game

AC only exposes its real-time telemetry through Windows Named Shared Memory.
That memory is only visible to processes running inside the same
Wine/Proton prefix as the game — there's no way to read it from a native
Linux process. That's not a design limitation of Victor, it's a limitation
of the data source: any reader, in any language, has to run under that same
Wine.

Given that, the question isn't "Wine or not" but what to run inside it. The
repo has two implementations of the same reader:

- [`src/victor/ac_shm_reader.py`](../src/victor/ac_shm_reader.py) — a
  reference implementation in Python/ctypes, explicitly documented in its
  own docstring as a reference implementation, not the one used in
  production.
- [`native/ac_shm_reader.c`](../native/ac_shm_reader.c) — the one
  `start.sh` launches, compiled with `x86_64-w64-mingw32-gcc`.

Both read the same structs (`SPhysics`/`SGraphic`/`SStatic`/`SCrewChief`,
with the same `#pragma pack(4)` CrewChief uses) and write the same JSON. The
difference between running a full CPython interpreter with ctypes bindings
under Wine versus running a compiled native binary with no runtime is what
pushes the production path toward C: less startup surface, and no need for
Victor's own dependencies (`piper-tts`/`onnxruntime`/etc.) to also exist
inside the Wine prefix. The cost is maintaining two implementations of the
same memory layout in parallel — if CrewChief or AC ever change the struct,
both need updating.

There's also a third path, kept only as a fallback
(`TELEM_FAST_BRIDGE`/`TELEM_SLOW_BRIDGE` in
[`engineer.py`](../src/victor/engineer.py)): a Python widget that runs
inside AC's own in-game app system (`ACEngineer.py`). That path requires
the widget to be open in the game and depends on AC's app system instead of
reading shared memory directly, which is why the standalone SHM reader is
the preferred source and the bridge is only used if the `.exe` in `native/`
isn't running.

### Why JSON on disk instead of IPC

The SHM reader (under Wine) and the `engineer.py` daemon (native Linux,
outside Wine) are separate processes on either side of that boundary.
Instead of building a socket or pipe that crosses it, the reader writes two
JSON files next to its own binary (`native/ac_telemetry_fast.json` at
~10 Hz, `native/ac_telemetry_slow.json` at ~1 Hz), and `engineer.py` polls
them by `mtime` — every 0.04s it checks whether the fast packet changed
(with a minimum 0.08s gate between reads), and every 0.5s it does the same
for the slow packet (see the loop in `engineer.py`, around where
`_pick_source` initializes).

The explicit trade-off: the two processes end up completely decoupled. The
reader can restart or crash without the daemon doing anything more than
detecting a timeout (`TIMEOUT_SECS = 3.0`; no new data in that window and it
declares itself disconnected and resets the spotter); the daemon can
restart without the reader caring. It's trivial to inspect live (just `cat`
the JSON) and doesn't require the two sides to agree on a binary or
versioned protocol. The cost is the latency and disk I/O the polling
introduces — checking a file every 40-80ms instead of receiving data by
push. There's no measurement of how much overhead this actually adds versus
a socket. **TODO: measure the real latency of this path (file write → value
available in `_current`) against a socket-based alternative before deciding
whether it's worth changing.**

### Why failover across LLM providers instead of a single one

Victor runs during a live race session — if the one configured LLM provider
goes down or starts rate-limiting mid-session, there's no practical way to
"restart" without losing the rest of the race. That's why
[`victor_brain.py`](../src/victor/victor_brain.py) chains four
OpenAI-compatible providers, all with a free tier: Groq → Cerebras →
NVIDIA NIM → Gemini. Each one has its own circuit breaker (3 consecutive
failures pause that backend for 5 minutes, `_BREAKER_FAILS` /
`_BREAKER_PAUSE_S`), so a downed provider isn't retried on every voice
turn — it's skipped straight to the next available one without burning time
on repeated timeouts. STT (transcription) follows the same pattern with two
tiers: Groq `whisper-large-v3` first, Deepgram Nova-3 if there's no response
or no recognizable content.

There's deliberately no local backend (Ollama) in the chain. The code
comment explains why: GPU and VRAM are already contended by the game and
the graphics stack during a session, and running a local model alongside AC
caused a freeze on 2026-07-03. A single cloud provider would be simpler to
maintain, but it's a single point of failure for something running live
during a race; the chain with a circuit breaker trades that simplicity for
resilience against a single provider's outages or rate limits.

## Constraints: what "real time" means here, and the latency budget per stage

Two very different latency classes coexist, and it's worth not treating
them as the same constraint:

**Spotter (deterministic, no LLM).** Reads the fast packet (which the SHM
reader writes at ~10 Hz) and runs a debounced state machine before
announcing anything: `SPOTTER_CONFIRM_S = 0.15` to confirm a rival is still
alongside before calling it, `SPOTTER_CLEAR_S = 0.8` before calling
"clear." That debounce isn't pipeline latency — it's a deliberate design
choice to avoid reacting to a single noisy/jittery frame in the overlap
detection. There's no LLM anywhere in this path, which is why the README
describes it as "<150ms": that figure corresponds to the code's own
confirmation threshold (`SPOTTER_CONFIRM_S`), not an instrumented
end-to-end measurement.

**Free-form voice queries.** The full path is: VAD (Silero, real, no mocks)
detects speech → recording → STT (Groq, with Deepgram as backup) → wake-word
filter on the transcribed text → if it passes, LLM completion (with
failover across the four providers) → Piper synthesis → playback via
`paplay`/`aplay`. This path **has no latency budget enforced in code** — no
assertion or test fails if it takes longer than X seconds. The only thing
that exists today is a post-hoc log line in `_handle_voice`
(`"[Piloto] respuesta lista en {t}s (transcripción + LLM)"`) meant to
diagnose, live, whether a "Victor was slow" report from the driver was the
STT, the LLM, or the failover jumping between backends — not an aggregated
or tracked value over time.

**TODO: no p50/p95 latency numbers have been collected for either path.**
The `_handle_voice` log gives one data point per turn, but nothing
aggregates it. Getting a real per-stage budget (VAD → STT → LLM → TTS →
playback) would require instrumenting each stage separately, not just the
total.

There's also a real-time constraint at the UX level, not the pipeline
level: non-critical messages (`priority >= 2`) are deferred if the car is
inside a braking zone mapped for that track (`_in_braking_zone()`), and only
played once the car leaves that zone — so Victor doesn't talk to the driver
while they're braking hard for a corner. Deferred messages older than 10s
(`_DEFERRED_STALE_S`) are dropped instead of being spoken late and out of
context. The spotter (`priority=0`) and urgent alerts bypass this filter.

## What I'd do differently starting today

- **Calibrate detection thresholds from day one, not after the fact.** The
  code itself flags this: the brake-lockup thresholds
  (`LOCKUP_SLIP_THRESHOLD`, `LOCKUP_BRAKE_THRESHOLD`) are commented as
  "first-pass thresholds, not yet calibrated against real data," unlike VAD,
  which already has a dedicated calibration flow
  (`tools/teach_victor.py`). Starting over, I'd build that same kind of
  calibration tool for the telemetry thresholds (lockup, temperature, wear)
  from the start instead of leaving them as estimates to adjust later "if
  they produce false positives on track."
- **Instrument per-stage latency from the start**, not a post-hoc total
  print. The free-form voice path is the slowest and most driver-visible
  one; without a per-stage breakdown (VAD, STT, LLM, TTS), any "it was
  slow" report means manually digging through logs instead of having an
  aggregated number.
- **Don't inherit the `NEXUS_*` environment-variable prefix.** The README
  itself calls this out as an oddity worth explaining: API keys are looked
  up under `NEXUS_*` names because Victor grew out of a larger personal
  project (nexus-core), even though that project isn't needed to run
  Victor. A dedicated prefix (`VICTOR_*`) from the start would have avoided
  having to explain that inheritance in public docs.
- **Write the shared-memory test bench (`shm_simulator.c` +
  `test_shm_pipeline.py`) earlier, not at v6.** Validating the struct
  layout against an independent simulator (derived from CrewChief's C#)
  is what uncovered that the spotter was "dead" with real SHM
  (`track_len` hardcoded to 0, per that version's own changelog). Having
  that bench from the first SHM integration would have caught the problem
  before it depended on testing on track.

Active development, daily personal use. 143 pytest tests, CI green on
